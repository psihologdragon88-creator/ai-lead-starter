Понять один раз

01Карта: где живут ваши файлы

Почти все вопросы по Git — это на самом деле вопрос «а где сейчас мой файл». Областей всего четыре, и команды просто перемещают файлы между ними.

1. Рабочая папка
Файлы как есть прямо сейчас. Git видит изменения, но ничего с ними не делает
панель: Changes
2. Индекс
«Стол перед сканером»: то, что вы выложили и что попадёт в следующий снимок
панель: Staged Changes
3. История
Сделанные и подписанные снимки. Лежат у вас на компьютере
панель: Graph / History
4. Удалённый репозиторий
Копия истории на сервере. Её видят коллеги, на неё есть ссылка
GitLab / GitHub
— add →
— commit →
— push →
← pull —
Главное следствие

Сделать коммит ≠ отправить. После коммита ваша работа существует только на вашем компьютере. Чтобы она появилась у коллег и по ссылке — нужен push. Это ошибка номер один у всех, кто начинает.

Не думайте про Git как про Яндекс.Диск. Диск синхронизирует сам и постоянно. Git — только когда вы явно сказали. Это главное отличие, и именно из-за неверной аналогии люди потом удивляются, почему на сервере пусто.
Настройка

02Настроить один раз на компьютере

Без этого не пройдёт самый первый коммит: Git откажется подписывать снимок, не зная, кто его делает.

git config --global user.name "Имя Фамилия"
git config --global user.email "почта@company.ru"

Проверить, что записалось:

git config --global --list
Почта здесь нужна не для писем, а чтобы сервер связал ваши коммиты с вашей учётной записью. Указывайте ту же почту, что в GitLab или GitHub — иначе ваши коммиты будут числиться за неизвестным автором.
Девяносто процентов работы

03Шесть ежедневных команд

git statusчто сейчас происходитсамая частая
Показывает: в какой вы ветке, какие файлы изменились, что уже выложено на «стол», а что нет. Если вы не понимаете, что происходит — начните с неё. В девяти случаях из десяти ответ будет прямо в выводе, вместе с подсказкой, какую команду выполнить дальше.
git status
Аналогия: посмотреть на свой рабочий стол и понять, что на нём сейчас лежит.
В Cursor: это и есть панель Source Control — Ctrl+Shift+G / Cmd+Shift+G. Разделы Changes и Staged Changes — то же самое, но картинкой.
git cloneзабрать пространство к себе
Скачивает репозиторий с сервера на ваш компьютер — целиком, вместе со всей историей. Это первая команда курса: так вы получите стартовое пространство с правилами, скиллами и этим справочником.
# GitLab
git clone https://gitlab.company.ru/группа/ai-lead-starter.git

# GitHub
git clone https://github.com/организация/ai-lead-starter.git
Аналогия: скачать себе общую папку проекта вместе с журналом всех её правок.
В Cursor: палитра команд Ctrl/Cmd+Shift+P → Git: Clone → вставить ссылку → выбрать, куда положить.
git addвыложить на стол
Помечает файлы как готовые к снимку. Нужна, потому что вы не всегда хотите зафиксировать всё, что изменили: часть работы может быть ещё сырой.
# конкретный файл
git add README.md

# всё, что изменилось в текущей папке
git add .
Аналогия: выложить на стол перед сканером те листы, которые собираетесь сфотографировать. Остальные остаются в стопке.
В Cursor: плюсик + справа от имени файла в панели Source Control. Файл переезжает в Staged Changes.
git commit -mсделать снимокядро
Сохраняет состояние выложенных файлов в историю — навсегда и с подписью. -m значит message: сообщение о том, что и зачем вы поменяли. По нему вы потом найдёте нужный момент.
git commit -m "описал свою рутину в README"
Аналогия: подписанная версия документа при согласовании. Не «сохранить файл», а «зафиксировать законченный смысловой шаг».
В Cursor: написать сообщение в поле сверху и нажать галочку Commit. Значок искры рядом с полем сгенерирует сообщение сам — прочитайте, что он написал, и поправьте: сообщение пишется для людей.
git pushотправить в общий репозиторийбез неё работы не существует
Отправляет ваши коммиты на сервер. До push ваша работа есть только у вас. Коллега её не видит, ссылка не работает, при потере ноутбука всё пропадает.
# обычно достаточно
git push

# в первый раз для новой ветки
git push -u origin имя-ветки
Аналогия: сохранить у себя — это ещё не отправить. Push и есть «отправить».
В Cursor: кнопка Sync Changes (или Publish Branch в самый первый раз).
origin — это просто короткое имя вашего сервера, чтобы не писать длинный адрес каждый раз. Посмотреть, куда именно он указывает: git remote -v.
git pullзабрать свежее
Скачивает изменения, которые появились на сервере, пока вы работали. Привычка: начинать работу с pull. Иначе вы правите устаревшую версию и потом разбираетесь с конфликтами.
git pull
Аналогия: перед правкой методички проверить, не выложил ли кто-то новую редакцию.
В Cursor: та же кнопка Sync Changes — она сначала забирает чужое, потом отправляет ваше.
Ради этого всё и затевалось

04Посмотреть и откатить

Эти четыре команды — главная причина, по которой вы вообще ставите Git, когда работаете с ИИ-агентом. Агент правит файлы целиком, и «отменить» внутри него нет.

git logистория снимков
Показывает, кто, когда и что коммитил. У каждого коммита есть уникальный номер — хэш, по нему к нему можно вернуться.
# коротко: по строке на коммит
git log --oneline -10
Аналогия: журнал изменений документа.
В Cursor: вкладка Graph / History в панели Source Control.
git diffчто именно изменилосьпосле работы агента
Показывает построчно, что поменялось с последнего снимка. Ваш главный инструмент контроля за агентом: он сказал «готово», вы смотрите, что он на самом деле сделал, — до того как это зафиксировать.
# что изменилось и ещё не выложено на стол
git diff

# конкретный файл
git diff AGENTS.md
Аналогия: режим «отображать исправления» в документе.
В Cursor: просто кликнуть на файл в панели Source Control — откроется сравнение «было / стало» двумя колонками. Удобнее, чем в терминале.
git restoreвернуть файл как былспасательный круг
Агент переписал файл, и вы хотите обратно. Возвращает файл к состоянию последнего коммита. Изменения, которых вы не коммитили, при этом теряются — на то и расчёт.
# вернуть один файл
git restore имя-файла.md

# убрать файл со «стола», не трогая его содержимое
git restore --staged имя-файла.md
Аналогия: закрыть документ без сохранения.
В Cursor: значок разворота (Discard Changes) напротив файла в панели Source Control.
Отсюда простое рабочее правило: перед тем как дать агенту задачу — сделайте коммит. Тогда откат всегда возможен и занимает две секунды. Без коммита откатывать не к чему.
git revertотменить уже сделанный коммит
Когда плохое изменение уже закоммичено и, возможно, отправлено. Создаёт новый коммит, который отменяет указанный: что добавляли — удалится, что удаляли — вернётся.
# сначала находим номер коммита
git log --oneline -10

# потом отменяем его
git revert a1b2c3d
Аналогия: сторнирующая проводка. Не стираем прошлое, а выпускаем документ, который его отменяет.
Почему именно так, а не «удалить коммит»: история остаётся целой, и у коллег ничего не ломается. Оба коммита — и ошибочный, и отменяющий — видны. Это правильно и безопасно.
Когда работаете не один

05Ветки: параллельные черновики

На курсе ветки обязательны только треку «Ускорение». Но понимать, что это, стоит всем: в общем репозитории вы столкнётесь с ними в первый же день.

git branch / git switchсоздать и перейти
Ветка — отдельная последовательность снимков, отходящая от общей. Вы правите свой черновик, не трогая утверждённую версию. Основная ветка обычно называется main или master.
# создать и сразу перейти — обычно нужно именно это
git switch -c моя-рутина

# вернуться на основную
git switch main

# посмотреть, какие ветки есть
git branch
Аналогия: переработка модуля программы в отдельном черновике. Не получилось — выбросили черновик, утверждённая версия цела.
В Cursor: имя текущей ветки — в левом нижнем углу. Клик по нему открывает список веток и создание новой.
В старых инструкциях для этого используется git checkout. Он до сих пор работает, но делает слишком много разного — и переключает ветки, и откатывает файлы. Поэтому его разделили на два понятных: switch для веток и restore для файлов. Берите новые.
git mergeсвести ветки в одну
Когда работа в вашей ветке закончена и её нужно вернуть в основную.
# переходим туда, КУДА вливаем
git switch main
git pull
git merge моя-рутина
Аналогия: свести правки двух рецензентов в один документ. Правили разные разделы — сведётся само. Правили один абзац — система остановится и спросит вас. Это называется конфликт, и это нормальная ситуация, а не поломка.
В Cursor: при конфликте открывается экран сравнения с кнопками «взять эту версию / ту / обе». Там же есть Resolve in Chat — можно отдать разбор агенту.
На практике в команде вы будете делать не merge руками, а merge request (в GitLab) или pull request (в GitHub) — через интерфейс сайта. Вы отправляете ветку кнопкой push, а дальше нажимаете «создать merge request», коллега смотрит изменения и подтверждает. Так правки проходят через проверку человеком.
Аварийка

06Я сломал — что делать

Ситуации в порядке частоты. Почти всё чинится одной строкой.

Коммит не проходит, пишет что-то вроде «please tell me who you are»
Не настроены имя и почта. Выполните две строки из раздела 02 — это делается один раз на компьютере, больше не повторится.
Агент переписал файл, хочу вернуть как было
Если вы ещё не коммитили после его правок — git restore имя-файла, либо значок разворота напротив файла в Cursor. Секунда, и файл вернулся к последнему снимку.
Если уже закоммитили — найдите предыдущий коммит через git log --oneline и верните оттуда: git restore --source=a1b2c3d имя-файла.
Случайно выложил на «стол» лишний файл
git restore --staged имя-файла. Файл уйдёт из Staged Changes, но его содержимое не изменится. В Cursor — значок минуса напротив файла.
Push отклонён: «updates were rejected» / «кто-то уже запушил»
На сервере появились изменения, которых нет у вас. Сначала заберите их, потом отправляйте: git pull, разберитесь с конфликтом, если он возникнет, затем git push. Никогда не решайте это через push --force — так вы сотрёте чужую работу.
Push просит логин и пароль или сразу отказывает
Не выполнен вход. Обычный пароль от учётной записи для push давно не работает — нужен вход через браузер или токен доступа.
В Cursor: палитра команд Ctrl/Cmd+Shift+P → GitHub: Sign in, для GitLab — токен, выданный администратором, вводится вместо пароля.
В панели изменений внезапно сотни файлов
Репозиторий создан не в той папке — обычно в домашней или в папке, где лежат все проекты сразу. Проверьте заголовок окна. Если папка не та: закрыть, удалить из неё скрытую папку .git, открыть нужную и начать заново.
Написал ерунду в сообщении коммита
Если вы ещё не сделали push — git commit --amend -m "правильное сообщение". Если уже отправили на сервер — оставьте как есть: переписывание отправленной истории ломает работу коллегам, а неудачное сообщение никому не вредит.
Не понимаю, где я и что происходит
git status, затем git log --oneline -5. Первая скажет, в какой вы ветке и что не зафиксировано, вторая — на чём вы остановились. Вывод git status почти всегда содержит подсказку, какую команду выполнить дальше — его стоит читать, а не пролистывать.
Закоммитил файл с реальными данными или паролем
Порядок строго такой:
1. Если это пароль, ключ или токен — сначала смените его в системе, которая его выдала. С момента попадания в репозиторий он считается скомпрометированным.
2. Только потом чистите репозиторий.
3. Если это персональные данные — зафиксируйте факт и сообщите ответственному, не решайте в одиночку.

«Я удалил файл следующим коммитом» не помогает: старый коммит остаётся в истории и доступен по прямой ссылке. На курсе самый быстрый способ — снести учебный репозиторий целиком и создать заново, там у вас три файла.
Граница

07Что не трогать, пока не понадобится по-настоящему

Эти команды вы встретите в статьях и видео. Они не «плохие» — просто у них есть последствия, которые новичок не предвидит. Для всего, что вы будете делать на курсе, они не нужны.

КомандаЧто делаетПочему не сейчас
git rebase Переносит коммиты, перестраивая историю Переписывает историю. В видео и статьях его часто советуют как способ влить ветку в основную. Для команды это спорная практика даже среди разработчиков, а для новичка — верный способ потерять работу. Вам нужен merge или merge request через интерфейс
git reset --hard Откатывает всё к указанному состоянию Молча удаляет незакоммиченную работу без подтверждения. Для отката одного файла есть безопасный git restore, для отмены коммита — git revert
git push --force Перезаписывает историю на сервере Стирает чужие коммиты. Если push отклонён — это не повод форсить, а сигнал сделать pull
git cherry-pick Переносит отдельный коммит из ветки в ветку Полезная вещь, но нужна при сложной работе с ветками. У вас такой работы на этапе 1 не будет
git stash Временно прячет незавершённые правки Удобно, но легко забыть, что вы что-то спрятали, и потерять. Проще сделать обычный коммит с пометкой «в работе»
Общее правило безопасности. Команды, которые добавляют в историю (commit, revert, merge), — безопасны: всегда можно вернуться назад. Команды, которые переписывают историю (rebase, reset --hard, push --force), — опасны. Пока вы не различаете эти два класса уверенно, пользуйтесь только первым. Его хватает на годы работы.
Площадки

08GitLab и GitHub: что меняется

Почти ничего. Git — это программа у вас на компьютере, а GitLab и GitHub — сайты, куда можно положить копию. Все команды из этого справочника работают одинаково на обеих площадках. Разница — в адресе, в том, как вы входите, и в названиях кнопок на сайте.

GitLab (внутренний)GitHub (внешний)
Команды gitПолностью одинаковые
Адрес для clonehttps://gitlab.company.ru/группа/проект.githttps://github.com/организация/проект.git
Как войтиКорпоративная учётная запись; для push — токен доступа вместо пароляВход через браузер из редактора
Предложить измененияMerge requestPull request
Группировка проектовГруппы и подгруппыОрганизации
Что сюда можно кластьРабочие материалы, фирменные шрифты и логотипы, внутренние регламентыТолько обезличенное. Никаких реальных ФИО, выгрузок, внутренних ссылок, фирменных ресурсов
Правило курса в одну строку

GitLab — это работа. GitHub — это полигон. На внешней площадке мы тренируемся и публикуем учебные артефакты по ссылке, поэтому туда идёт только обезличенное. Всё, что связано с реальными материалами, корпоративным стилем и внутренними документами, живёт во внутреннем контуре.

Практический вывод для вас как для человека, который учится: не бойтесь, что «учили на одном, а на работе другое». Вы учите Git, а не сайт. Переход между площадками — это смена одной строки с адресом.

Четыре правила, которые важнее команд

  1. Перед тем как дать агенту задачу — сделайте коммит. Это ваша точка возврата.
  2. Коммит — не Ctrl+S. Фиксируйте законченный смысловой шаг, а не каждое сохранение файла.
  3. Сделал шаг — commit и push. Не в конце дня: до push работа существует только у вас.
  4. Если файл нельзя отправить внешнему подрядчику по почте — он не идёт ни в репозиторий, ни в чат с ИИ, ни на публикацию.
Если совсем застряли

Выполните git status, скопируйте весь вывод целиком и покажите его агенту в чате Cursor с вопросом «что происходит и что мне сделать». В стартовом пространстве для этого есть отдельный скилл — git-helper. Это, пожалуй, самый честный способ применения ИИ на первом уроке: инструмент объясняет вам собственную ошибку.
